# 專案審視

產出是給使用者決策的清單。重精準不重數量：證據不夠的項目寧可不列。
第 6 步之前不改任何檔案。

## 0. 先確認能派 subagent

這個流程要派出彼此獨立的 subagent（審視者 3 個、裁判 1 個）。做不到時停下來告訴使用者「這個環境不能用這個 skill」，
**不要改成自己依序扮演各角色**：審視者與裁判共用上下文，裁判就失去作用。

## 1. 確認輸入

- **範圍**：使用者沒指定就是整個 repo。
- **角色**：預設下表三個；使用者指定時替換或增減。
- **排除項**：使用者說不要再提的項目，原文帶給審視者。

| 角色 | 看什麼 |
|---|---|
| 使用者介面與體驗 | 操作流程、錯誤與提示訊息、i18n 是否完整、設計變數是否一致、無障礙 |
| 業務邏輯 | 規則漏洞、邊界條件、權限與狀態轉換、前後端規則不一致 |
| 延伸與優化 | 缺少的能力、可以簡化的地方、效能與維運 |

## 2. 並行派出審視者

每位拿到 [`reviewer.md`](reviewer.md) 全文，加上自己的角色、「看什麼」、範圍與排除項。不給其他審視者的角色。

## 3. 格式檢查

收齊後只檢查格式，不判斷內容：

- 證據少於 2 個、缺影響情境的項目剔除；超過 5 項的只留前 5 項（審視者已依影響排序）。
- 記下剔除了哪些、為什麼，放進最後的清單。
- 全部是 0 項就直接回報使用者，不派裁判。

## 4. 派出裁判

另派一個新的 subagent，給 [`judge.md`](judge.md) 全文與通過檢查的項目。
**只給項目本身**，不給審視者的指示、角色說明或主 agent 的看法。

## 5. 列出決策清單

照裁判的結果在對話裡列出，不寫成檔案：

```text
## 支持
1. <標題> — <一句摘要>
   - 理由：<裁判的理由>
   - 規模：小／中／大；依賴：<其他項目或「無」>
## 延後
1. <標題> — <一句摘要>
   - 理由：<…>；等到：<條件>
## 反對
1. <標題> — <反對的理由>；相關 ADR：<編號或「無」>
## 格式檢查剔除
- <標題>：<原因>
```

主 agent 不推翻裁判。意見不同時，在該項下面加一行「主 agent 的看法」。
問使用者要執行哪幾項，以及反對的項目是否同意。

## 6. 補記反對的決定

只記使用者同意的反對項目，草稿先給使用者確認才寫入：

- **碰到現有的 ADR**：照 [`decisions/README.md`](../../../docs/decisions/README.md)〈寫法〉記進那一份：
  還沒有 `v*` tag 就直接併進「背景」或「後果」，有 tag 之後追加 `## 後續討論`。
- **沒碰到 ADR、但屬於「刻意不做」的取捨**（之後很可能又被提出）：另寫一份新的 ADR。
- **只是效益太小**：不記錄，下次可以用排除項擋掉。

支持的項目不記（做完問題就不存在），延後的也不記（下次由裁判重新檢查條件）。

補記走一個獨立的 docs PR，排在實作項目之前。之後選定的項目各自照 `feature-workflow` 開 PR，一次一個。
