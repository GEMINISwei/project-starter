# 插隊修正正式環境

平常一次只有一個進行中的 PR（[說明](../../../docs/workflow.md#一次一個-pr)），守衛會攔下開新分支。
這個流程是唯一的例外出口：**要不要插隊由使用者決定**，agent 不自己判斷「這個夠急」。

## 1. 說明並取得同意

先向使用者說明：

- 正式環境發生什麼事、影響誰、有沒有暫時的處理方式
- 為什麼等不及目前開著的 PR（列出 PR 號碼與狀態）
- 打算怎麼修、修正分支的名稱（`fix/<kebab-case>`）

使用者同意之後才往下。不同意就回到原本的 PR，把這個問題記下來，等合併後照平常流程做。

## 2. 開修正分支

開分支時守衛會攔下，照它的說明讓使用者確認（申請指令會再跳一次確認，這是預期的）。
修正分支一定**從最新的 `main` 開**，不要從進行中的分支開：插隊的修正不能帶著還沒審過的程式上線。

## 3. 修正

照 `feature-workflow` 的第 2～7 步做，範圍收到最小：

- 驗收條件只寫這個問題，同樣先給使用者確認
- 先寫能重現問題的測試，確認是紅燈，再修
- 不順手整理別的東西，也不把進行中 PR 的內容搬過來

## 4. 合併與發版

合併由使用者做。需要立刻上線時照 `release` skill 發版，發布前一樣要使用者同意。

## 5. 回到原本的 PR

1. 切回原本的分支，跟上最新的 `main`（`git merge origin/main`；不要 rebase 已經被審查過的 commit）
2. `make check`，有衝突或紅燈照平常的流程處理
3. push 之後照 `watch-pr` 等 CI，告訴使用者原本的 PR 已經跟上
