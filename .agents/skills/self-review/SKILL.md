# 交給使用者審查前的自我檢查

目的是讓使用者審查時拿到整理好的重點，不必從頭讀 diff 才發現問題。這一步只整理與回報，
發現要改的地方照平常的流程改（改測試仍要先經使用者同意）。

先取得整份 diff：`git diff origin/main...HEAD`，與 `gh pr view <PR 號碼>` 的描述。

## 1. 驗收條件逐條對照

PR「驗證」段的每一條：

- 對應的測試存在、名稱一致，而且真的驗證到那個條件（不是只呼叫到、沒有斷言）
- 結果寫上了（通過或失敗都寫）

diff 裡有改動但對不上任何一條驗收條件的，列出來：要嘛是漏寫的條件，要嘛是範圍外的改動。

## 2. 範圍

- 只做這個分支的那件事：順手改的格式、重新命名、無關的修正，拆出去另開 PR
  （[說明](../../../docs/workflow.md#開發流程)）
- 沒有多出驗收條件沒要求的抽象層、設定項或擴充點

## 3. 繞過檢查的寫法

`make check` 會放行這些，CI 的 `pr` 會擋（[說明](../../../docs/workflow.md#開發流程)），送出前先自己對過：

- 新增的抑制註解：`noqa`、`type: ignore`、`eslint-disable`、`ts-expect-error`、測試的 skip。
  每一個都要在同一行寫理由，沒有理由的改掉
- 實作開始之後改過的測試檔（經使用者同意的，PR 描述要寫明原本的斷言為什麼錯）
- 防線本身的檔案（清單見 [`agent-hooks.md`](../../../docs/extending/agent-hooks.md#防線檔案)，改的時候已經經過使用者同意）、
  `AGENTS.md` 與 skills：有改到就列進「檢查」段，說明改了什麼、為什麼，以及會不會讓哪一項檢查變寬鬆

## 4. 文件

- 行為或規則有變的，`AGENTS.md`、`docs/` 與相關的 skill 已經一起改
- 文件裡提到的指令、檔名、設定還對得上現在的程式

## 5. 整理進 PR 描述

- 「摘要」對上最新的 diff
- 「驗證」每條有結果
- 「檢查」列出上面找到、要使用者確認的事；diff 看得出來的不用列

回報使用者時，把第 1～4 節找到的問題與處理方式一起說明，沒找到問題也說一聲。
