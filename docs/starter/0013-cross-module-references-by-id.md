# 0013. 跨模組只以 ID 參照，但保留外鍵與共用交易

規則見 [`architecture.md`](../architecture.md#模組之間的資料關聯)，做法見
[`extending/cross-module.md`](../extending/cross-module.md)。

## 決定

- **程式層照嚴格的模組化單體**：`public.py` 只轉出函式與回傳型別，不轉出 ORM 類別或 `Table`（架構測試擋），
  跨模組不建 ORM 關聯。
- **資料庫層刻意偏離**：跨模組照樣建外鍵（用字串宣告），跨模組的呼叫也共用同一個 session 與交易。
- 反方向的需求（被參照的一方要知道誰在參照它）用資料庫的 `RESTRICT`（平台轉成 409）與**行程內的模組事件**。
  事件處理函式在發布者的交易裡同步執行，不做「提交之後才執行」。
- 非 HTTP 入口（CLI、worker）一律經過 `platform_scope()`，與 HTTP 請求共用同一組設定。

## 為什麼

這個模板主要由 AI 協作開發。AI 遇到「需要別的模組的資料」時，最省事的寫法是 import 對方的 ORM 類別直接 JOIN；
每次單獨看都合理，累積起來模組就糾纏在一起，「整包刪除」與「改內部不影響別人」都不再成立。
只以 ID 參照時，改一個模組的資料表，只要 public 的函式不變，其他模組就不受影響；審查時看 `public.py` 的 diff
就知道有沒有新的耦合。

主流做法有三派：框架預設（Django、Rails）跨模組隨意建 ORM 關聯與外鍵；模組化單體（Spring Modulith、Shopify 的
Packwerk）程式層只以 ID 參照、經由 public API 與行程內事件往來，資料庫通常也不建跨模組外鍵、甚至每個模組一個
schema，交易也避免跨模組；微服務則每個服務一個資料庫。

資料庫層不跟著嚴格派走：api 維持單一行程（[0004](0004-single-api-process.md)），沒有拆成服務的計畫，
嚴格派為了保留拆分的路而放棄的資料一致性，這裡用很低的成本就拿得到。

事件不做「提交之後才執行」：那種處理函式在行程於提交後、執行前中斷時會遺失，要可靠只能靠佇列，
所以寄信、呼叫外部服務這類副作用交給背景工作（[0005](0005-postgres-job-queue.md)）。
事件訂閱表要在每個入口設定，所以非 HTTP 入口也要經過 `platform_scope()`。

不採用的做法：

- **完全不用 ORM**：失去 Alembic autogenerate 與型別化的查詢，問題也不在 ORM 本身，而在它跨出模組。
- **合併 users 與 roles**：兩者需要的跨模組能力只有三個（取角色、取超管角色 id、展開權限），都是有意義的能力，
  依〈[先決定怎麼切模組](../architecture.md#先決定怎麼切模組)〉應該分開；roles 也是新增模組時照抄的範本。

## 代價

- 比 JOIN 多查詢：身分來源每個請求固定三次查詢（約 1 毫秒以內），不隨筆數增加。
- 用對方欄位排序後分頁、跨模組報表這類一定要 JOIN 的需求，要用去正規化或唯讀 view 這種明確的例外。

## 什麼時候重新檢討

真的要把某個模組拆成獨立服務時：先寫一支 migration 拿掉它的跨模組外鍵，並把共用交易改成事件。
